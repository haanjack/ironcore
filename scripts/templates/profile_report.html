측정한 workload

Steady tokens/s는 profiler를 끈 별도 실행의 첫 10 updates를 제외한 평균이다. Profile tokens/s는 shapes·Python stack·memory 기록의 overhead를 포함하므로 speedup 계산에 사용하지 않는다. Reference의 steps와 제외한 warmup은 아래 provenance에 기록한다.

Window는 이 device의 첫 CUDA activity 시작부터 마지막 종료까지다. Activity union은 stream 간 overlap을 한 번만 센다. “Compute와 겹치지 않은 NCCL”은 관측 구간의 차집합이며 training critical path나 제거 가능한 통신 비용을 뜻하지 않는다. Activity 미기록 시간은 GPU utilization이나 CPU bottleneck의 직접 측정값이 아니다.

같은 run의 rank 비교

각 device의 window 내 interval union이다. 두 rank의 NCCL duration 차이는 peer 대기·launch 순서·profiling overhead도 반영하므로 동일 collective의 순수 전송 속도 차이로 해석하지 않는다.

CUDA category와 phase

Category 누적 시간

Kernel launch의 CPU phase

Category는 kernel 이름에 따른 규칙 분류다. GEMM/attention/routing/pointwise/기타 kernel을 compute로, 명시적인 copy/memset을 memory로 센다. 각 행은 event duration의 합으로 서로 겹칠 수 있다. Phase는 CUDA launch correlation → CPU runtime → 명시적 표식/동일 시각의 backward 구간으로 대응한다. 비동기 실행의 GPU 종료 시각을 CPU phase 경계로 자르지 않는다.

두 rank의 CUDA timeline

구간 이동

가로축은 이 run의 첫 CUDA activity부터의 ms, 세로축은 rank/device/stream이다. Tooltip에서 실제 duration과 전체 kernel 이름을 확인한다. 짧은 event의 표시 폭은 픽셀 해상도의 영향을 받으므로 busy 비율은 위의 interval-union 수치로 읽는다. Rank 시간은 trace의 baseTimeNanoseconds로 같은 host 시간축에 정렬하며 CUPTI clock calibration의 정밀도 이상으로 해석하지 않는다. 필터는 timeline과 kernel 목록에만 적용한다.

Collective communication

관측한 NCCL GPU kernels

NCCL CPU 호출과 tensor payload

Payload는 annotation의 input shape × dtype bytes로 계산한 logical tensor 크기다. NCCL wire traffic, NVLink throughput 또는 실제 전송 byte 수가 아니다. CPU NCCL 호출과 GPU kernel은 1:1일 필요가 없다. NCCL kernel duration에는 peer 대기와 synchronization이 포함될 수 있으며 이를 순수 네트워크 latency로 단정하지 않는다.

주요 CUDA kernels

선택 rank의 누적 시간이 큰 순서로 최대 35개를 표시한다. Category 체크박스와 검색을 적용할 수 있다. 각 항목의 시간을 합쳐 wall-clock 점유율로 계산하지 않는다.

주요 CPU operators

CPU inclusive duration의 합이다. Parent/child operator와 여러 thread가 겹치므로 이 표의 합을 CPU wall-clock으로 사용하지 않는다. nonzero/index/scalar extraction은 host synchronization과 작은 연산의 빈도를 조사할 단서지만 원인별 최적화 효과는 별도 ablation이 필요하다.

해석과 재현

작은 MoE에서 active parameter 수가 낮다는 사실만으로 높은 처리량이 보장되지는 않는다. Expert별 GEMM, routing·indexing, CPU launch와 NCCL을 함께 확인한다. Accumulation 횟수는 run 설정의 global/micro batch와 DP 크기에 따라 달라지며, TP는 같은 samples를 함께 처리한다. MoE auxiliary loss는 microbatch 단위라 이 구성 사이의 목적함수·품질 동등성을 주장하지 않는다.

Profile은 두 rank를 모두 수집하며 각 run의 profiler schedule에 따른 active updates를 캡처했다. 실제 캡처된 update 번호와 source hash는 아래에 있다. SM utilization·메모리 bandwidth·NCCL wire throughput·critical-path 통신 비용을 이 trace만으로 확정하지 않는다. 불완전하거나 다른 길이의 rank window를 summed durations만으로 직접 비교하지 않는다.

이 trace의 MoE는 EP=1이며 DP/TP collectives를 다룬다. EP=2의 후속 수치·ownership·재개 검증과 지원 topology는 분산 학습 보완 노트에 있다.

CUDA_VISIBLE_DEVICES=0,1 torchrun --standalone --nproc_per_node=2 \
  scripts/benchmark_training.py --data-dir /tmp/ironcore-corpus \
  --output /tmp/moe-profile --model-size 50m --moe \
  --context 1024 --micro-batch 2 --global-batch 8 --steps 16 --warmup 10 \
  --profile --profile-ranks 0,1

Dense는 --moe를 생략하고 TP는 --tp 2를 추가한다. HTML 재생성 도구는 scripts/build_profile_report.py다. 원본 trace는 임시 실행 위치에 있고 HTML에는 compact GPU event와 수치 요약을 담았다.
